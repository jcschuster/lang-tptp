# lang-tptp — monorepo outline

Editor language support for TPTP, generated from the TPTP World `SyntaxBNF`:

| Package | Target | Primary consumers |
|---|---|---|
| `tree-sitter-tptp` | tree-sitter grammar + queries + `.wasm` | Zed, Neovim, Helix; Monaco (optional, see §5.3) |
| `codemirror-lang-tptp` | CodeMirror 6 language (Lezer) | Livebook smart cell (`kino_tptp`), web tools |
| `monaco-tptp` | Monaco language (Monarch tokenizer + config) | Monaco-based web tools |

Status: plan. Nothing below has been run against the BNF yet; statements about how the
BNF will translate are expectations and are marked as such.

---

## 1. Principles

1. **One BNF frontend.** The generator reuses `Tptp.Bnf` from `jcschuster/tptp` (pinned).
   `lang-tptp` does not vendor its own copy of `SyntaxBNF`; the BNF version is whatever the
   pinned `tptp` vendors.
2. **Layer discipline as in `tptp`.** `::=` → grammar, `::-`/`:::` → tokens, `:==` → not used.
   Editors accept what `tptp4X` accepts; semantic restrictions stay in the linter.
3. **Generated sources are committed** and checked with `mix lang_tptp.gen --check`, mirroring
   `mix tptp.gen --check` and `generated.yml`.
4. **Departures are listed per target**, rendered from the code that makes them
   (same pattern as `Tptp.Bnf.Generator.departures/0`), and printed by the Mix task.
5. **One highlight table.** All three targets get their highlighting from one hand-written
   mapping, so they cannot drift apart.
6. **One toolchain definition.** `flake.nix` + `flake.lock` pin every tool; CI runs the same
   devshell (§8).

## 3. Generator (`gen/`)

### 3.1 Pipeline

```
Tptp.Bnf.vendored_path!() ─► Tptp.Bnf.read!/1 ─► LangTptp.IR
                                                  ├─► TreeSitter  → packages/tree-sitter-tptp/grammar.js
                                                  ├─► Lezer       → packages/codemirror-lang-tptp/src/tptp.grammar
                                                  ├─► Monarch     → packages/monaco-tptp/src/monarch.ts
                                                  └─► Highlights  → highlights.scm, highlight.ts, Monarch classes
```

`mix lang_tptp.gen` writes all outputs and prints the BNF version and every target's
departures. `--check` renders into memory and fails on any difference.

### 3.2 IR

- **Syntactic rules** (`::=`): nonterminals with alternatives of `{:ref, _}` / `{:literal, _}`,
  as `Tptp.Bnf.Rule` already provides. Literal runs are split into terminals the same way
  `Tptp.Bnf.Generator` does (longest match against the known spellings).
- **Token rules** (`::-`, `:::`): parsed into a **regex AST** (alternation, sequence, class,
  negated class, repetition, optional, escape, reference). `Tptp.Bnf.Oracle` substitutes text
  into PCRE, which is enough for Elixir but not for three different target syntaxes.
- **Repetition** (`X*` in `::=` rules): kept as a repetition node; tree-sitter and Lezer both
  have `repeat`/`*`, so the right-recursive helper nonterminal that yecc needs is not required.

### 3.3 Regex printers

| Target | Syntax | Notes |
|---|---|---|
| tree-sitter | JS regex literal in `grammar.js` | Compiled by tree-sitter's own regex engine. No octal escapes: print BNF `\40` as `\x20`. |
| Lezer | `@tokens` syntax (`$[a-z]`, `![…]`, `"…"`, `+`, `*`, `?`) | Not regex. Character classes and literals must be printed in Lezer form. |
| Monarch | JS regex | Same escape rule as tree-sitter. |

The existing oracle can serve as the test: for every token rule, the printed JS regex must
accept/reject the same samples as the PCRE pattern from `Tptp.Bnf.Oracle.patterns/1`.

### 3.4 Departures per target (expected, unverified)

| Issue in yecc | tree-sitter | Lezer |
|---|---|---|
| `inference` / `introduced` / `file` as keyword and `<atomic_word>` | Probably none needed: the lexer only considers tokens valid in the current state; `word: $ => $.lower_word` + keyword extraction | `@extend` (both readings) rather than `@specialize` |
| `$thf` … `$let` reserved | `$let` probably needs `prec` or a `conflicts` entry | `@extend`/`@specialize` on the defined word, possibly `~` ambiguity markers |
| Statement keywords promoted by `Tptp.Splitter` | Probably none needed (state-dependent lexing) | `@extend` |
| `$`-language markers kept as children | Not an issue: both produce concrete syntax trees with all tokens | Same |

Each back-end exposes `departures/0`; the task prints them; a new conflict fails
generation instead of being absorbed.

### 3.5 Highlight table (`categories.exs`)

One map from BNF symbols (optionally in context) to categories, for example:

| BNF symbol | Category | tree-sitter capture | Lezer tag | Monarch class |
|---|---|---|---|---|
| `thf` `tff` `fof` `cnf` `tpi` `include` | statement keyword | `@keyword` | `keyword` | `keyword` |
| `<formula_role>` | role | `@keyword.modifier` | `modifier` | `type` |
| `<upper_word>` (variable) | variable | `@variable` | `variableName` | `variable` |
| `<defined_functor>`, `<defined_type>` | builtin | `@function.builtin` | `standard(name)` | `predefined` |
| `<system_functor>` | system | `@function.macro` | `special(name)` | `annotation` |
| `<single_quoted>`, `<distinct_object>` | string | `@string` | `string` | `string` |
| `<integer>` `<rational>` `<real>` | number | `@number` | `number` | `number` |
| connectives, quantifiers | operator | `@operator` | `logicOperator` | `operator` |
| comments | comment | `@comment` | `lineComment` / `blockComment` | `comment` |

Exact capture names should follow the conventions of the main consumers (Zed and Neovim
differ slightly); the table is the place to decide that once.

### 3.6 Coupling to `tptp`

`gen/` depends on `Tptp.Bnf`, `Tptp.Bnf.Rule` and, for the oracle test, `Tptp.Bnf.Oracle`.
These are internal to `tptp`. Pinning a commit makes this safe; the alternative is a
versioned JSON export from `tptp` (`mix tptp.bnf.export`) as a stable interface (§10).

For local work on both repositories, let `mix.exs` switch to a path dependency:

```elixir
defp tptp_dep do
  case System.get_env("TPTP_PATH") do
    nil -> {:tptp, github: "jcschuster/tptp", ref: "<sha>"}
    path -> {:tptp, path: path}
  end
end
```

## 4. Shared rules for all packages

- Package versions are independent of the BNF version. Each package records the BNF version
  it was generated from (`package.json` → `"tptp": { "bnf": "9.3.1.3" }`, and in the README).
- `fixtures/` holds small hand-picked files: every dialect (THF, TFF, TCF, FOF, CNF, TPI),
  `include`, annotations with `inference(…)`, TSTP derivations, and the edge cases from
  `tptp`'s tests (`fof(fof, axiom, p).`, `$let`, `$fot` vs `$fof`).
- Scope: TPTP problems and TSTP solutions (same BNF). The SZS ontology BNF is out of scope
  unless decided otherwise (§10).

## 5. Packages

### 5.1 `tree-sitter-tptp`

- **Scaffold** once with `tree-sitter init`, then replace `grammar.js` with the generated one.
  Keep `tree-sitter.json`, bindings and `package.json` hand-maintained.
- **Hand-written parts:** `extras` (whitespace, `%` line comments, `/* */` block comments),
  `word`, `conflicts`/`prec` overrides (fed from the generator's departure list), and all
  queries except `highlights.scm` (`folds.scm`, `indents.scm`, `brackets.scm` as wanted).
- **Committed generated output:** `grammar.js`, `src/parser.c`, `src/grammar.json`,
  `src/node-types.json`. Editors that build from the repository need `src/`.
- **Tests:** `tree-sitter test` (`test/corpus/*.txt` with expected trees,
  `test/highlight/*.p` with assertion comments).
- **Artifacts:** `tree-sitter build --wasm` → `tree-sitter-tptp.wasm`, attached to the
  GitHub release and shipped in the npm package.
- **ABI:** check that the ABI the CLI emits is supported by the target editors' tree-sitter
  versions before the first release; `tree-sitter generate --abi` can lower it.

### 5.2 `codemirror-lang-tptp`

- **Start from** `codemirror/lang-example` (the official template), replace its grammar.
- **Generated:** `src/tptp.grammar`, `src/highlight.ts`.
- **Hand-written:** `src/index.ts` — `LRLanguage.define` with `foldNodeProp`,
  `indentNodeProp`, `closeBrackets`, `commentTokens: { line: "%", block: … }`, and the export
  `tptp()` returning `LanguageSupport`.
- **Build:** `lezer-generator` turns the grammar into `parser.js` at build time
  (not committed).
- **Tests (mocha, as in the template; Vitest optional):** every fixture parses without error nodes; highlighting snapshot per
  fixture; the edge cases from §4 produce the expected node names.
- **Diagnostics stay out of this package.** In Livebook they come from `Tptp` on the BEAM via
  `@codemirror/lint` in the smart cell; `codemirror-lang-tptp` only provides the language.

### 5.3 `monaco-tptp`

- **Generated:** `src/monarch.ts` — states for top level, inside a statement, quoted atoms,
  distinct objects, block comments; keyword lists and token regexes from the BNF.
- **Hand-written:** `src/configuration.ts` (comments, brackets, auto-closing pairs, word
  pattern), `src/index.ts` (`register(monaco)`).
- **Limitation:** Monarch is a regex state machine, not a parser. It cannot tell a role from
  a functor by grammar position beyond what states encode.
- **Optional second layer (later):** a semantic-token provider that runs
  `tree-sitter-tptp.wasm` through `web-tree-sitter` and maps `highlights.scm` captures to
  Monaco tokens. Gives Monaco the same structure-aware highlighting as tree-sitter editors,
  at the cost of shipping the WASM runtime. Decide after the first release.
- **Tests:** tokenize every fixture, assert no `invalid` tokens, snapshot the token stream.
  Monaco's tokenizer expects a DOM; run these tests either in Vitest's jsdom environment or in
  Vitest browser mode with Playwright. Which one works with the current `monaco-editor` needs
  trying.

## 6. Testing strategy

### 6.1 Generator tests (`gen/test`)

- Regex printers agree with `Tptp.Bnf.Oracle` on generated samples (property tests).
- `departures/0` of each target matches what the generated grammar actually contains.
- `--check` round-trip.

### 6.2 Package tests

As in §5: tree-sitter corpus and highlight tests, Lezer parse/snapshot tests, Monarch token
tests, all over `fixtures/`.

### 6.3 Differential corpus test

Compare accept/reject over the TPTP library:

- `Tptp.parse/1` (reference)
- tree-sitter: a tree with an `ERROR` or `MISSING` node counts as reject
  (`tree-sitter parse --quiet` over a file list)
- Lezer: a tree with an error node counts as reject (Node script using the built package)

The runner writes one report (per file: three verdicts) and fails on disagreement, except for
entries in an explicit allow-list with a reason. Budget as in `tptp`'s `corpus.yml`: one file
in five on pull requests, the whole library nightly.

Monarch is not part of the differential test; it has no notion of accept/reject.

## 7. CI workflows

All jobs run inside the flake devshell (`nix develop --command …`), so CI and local builds use
the same tool versions.

| Workflow | Trigger | Steps |
|---|---|---|
| `generated.yml` | push, PR | `mix lang_tptp.gen` → `tree-sitter generate` (in `packages/tree-sitter-tptp`) → `git diff --exit-code` |
| `ci.yml` | push, PR | `mix test` (gen); `tree-sitter test`, `tree-sitter build --wasm`; `pnpm -r build`; `pnpm -r test` |
| `corpus.yml` | PR (paths), nightly, manual | download TPTP library (as in `tptp`), build packages, run §6.3 |
| `release.yml` | release PR merged / tag | publish npm packages; attach `.wasm` to the GitHub release; optional crates.io |
| `bump-tptp` | Renovate/Dependabot on the `tptp` dependency | PR that updates the pin; `generated.yml` then shows the grammar diff for a new BNF |

**Releasing `tree-sitter-tptp` from a subdirectory.** The reusable workflows in
`tree-sitter/workflows` (`release.yml`, `package-npm.yml`, `package-crates.yml`) have no input
for a grammar in a subdirectory. Two options:

1. Own publish steps with `working-directory: packages/tree-sitter-tptp`.
2. A release job that mirrors the subdirectory into a standalone `tree-sitter-tptp`
   repository. Editors that fetch grammars by repository URL + revision then get the usual
   layout.

Option 1 is enough to start; option 2 is worth it once editor integrations are published.

## 8. Releases and versioning

- Your commits already follow Conventional Commits (Zed's commit-message instruction), so
  **release-please in manifest mode** fits: one release PR per package, versions and
  changelogs derived from commit scopes (`feat(tree-sitter): …`). Extra version files
  (`Cargo.toml`, `tree-sitter.json`) can be listed per package.
- Alternative: Changesets, which needs a changeset file per change but is independent of
  commit messages.
- npm names: `tree-sitter-tptp` (tree-sitter convention, keep exactly), `codemirror-lang-tptp`
  (community convention; `@codemirror/` is reserved for official packages), `monaco-tptp`.

### 9.2 What is missing — put it in the devshell, not in the system config

Nothing needs to be installed system-wide. Everything goes into `lang-tptp/flake.nix`:

| Tool | nixpkgs attribute (version at your pin) | Needed for |
|---|---|---|
| Node.js | `nodejs_24` (default `nodejs`) | Lezer generator, builds, tests |
| pnpm | `pnpm` (= `pnpm_12`) | workspace |
| tree-sitter CLI | `tree-sitter` (0.26.11) | `generate`, `test`, `build --wasm`, `parse` |
| Erlang/Elixir | `beam28Packages` or `beam29Packages`, `elixir_1_20` (1.20.4) | `gen/` |
| C compiler | provided by `mkShell`'s stdenv | `tree-sitter test` compiles the parser |
| python3, gnumake | `python3`, `gnumake` | only for the Node binding of `tree-sitter-tptp` (node-gyp) |
| cargo | `cargo`, `rustc` | only if you publish to crates.io / test the Rust binding |

Everything else (`@lezer/generator`, `@codemirror/*`, `monaco-editor`, `vitest`,
`web-tree-sitter`, release tooling) comes from npm via `pnpm-lock.yaml`.

**Versions to decide:**

- **tree-sitter CLI:** nixpkgs has 0.26.11; npm's `tree-sitter-cli` is at 0.27.1. The
  generated `src/parser.c` depends on the CLI version, so use exactly one source. With CI
  running the devshell, nixpkgs is that source. If you want 0.27, use the npm package
  `tree-sitter-cli` as a pinned devDependency instead (it downloads a prebuilt binary, which
  runs on your machine through nix-ld) and drop `tree-sitter` from the flake.
- **OTP:** `tptp`'s CI uses OTP 28.0 / Elixir 1.20.3; your system uses OTP 29 / Elixir 1.20.
  Pick one for both repositories.

### 9.3 `tree-sitter build --wasm` on NixOS

Since tree-sitter 0.26.1, `build --wasm` uses wasi-sdk and downloads it on first use; no
Emscripten or container is needed. The download is a foreign binary. With your nix-ld
libraries it will probably run, but I have not tested that. If it does not, either set
`TREE_SITTER_WASI_SDK_PATH` to a working wasi-sdk, or build the `.wasm` only in CI (GitHub's
Ubuntu runners run the download without problems).

### 9.4 Playwright (only if Monaco tests need a browser)

npm's Playwright downloads browsers that do not run on NixOS. Use nixpkgs'
`playwright-driver.browsers` with `PLAYWRIGHT_BROWSERS_PATH`, and pin `@playwright/test` to the
same version as nixpkgs' `playwright-driver` (1.63.0 at your pin; npm is at 1.64.1). A
mismatch makes Playwright look for browser builds that are not there.

### 9.6 First steps

1. Repository and devshell: `jj git init --colocate`, `flake.nix`, `.envrc`, `direnv allow`.
2. Root workspace: `package.json` (`"private": true`), `pnpm-workspace.yaml` with
   `packages: [packages/*]` and `allowBuilds: { tree-sitter: true }` (pnpm 12 fails the
   install on unreviewed build scripts).
3. `packages/tree-sitter-tptp`: `tree-sitter init` (parser name `tptp`, bindings `c` + `node`),
   then remove the `tree-sitter-cli` devDependency so the Nix CLI is the only one, add
   `repository.directory`, and smoke-test with `tree-sitter generate`, a one-case corpus,
   `tree-sitter test`, `pnpm test`, `tree-sitter build --wasm`.
4. `packages/codemirror-lang-tptp`: copy of `codemirror/lang-example` without `.git`,
   `EXAMPLE` renamed in `package.json`, `src/index.ts`, `test/test.js`; own `LICENSE`.
5. `gen/`: `mix new gen --app lang_tptp_gen --module LangTptp`, `tptp` as dependency
   (`branch: "main"`, pinned by `mix.lock`, `TPTP_PATH` override), check that
   `Tptp.Bnf.read!/1` works from there.
6. `monaco-tptp` waits until the generator emits a first Monarch tokenizer.

## 10. Open decisions

1. **Generator interface:** depend on `Tptp.Bnf` internals (pinned commit) or add a versioned
   JSON export to `tptp`. The export is better if `tptp` goes to Hex without exposing
   `Tptp.Bnf`, or if other consumers appear.
2. **OTP version** shared with `tptp` (28 or 29).
3. **tree-sitter CLI source:** nixpkgs (0.26.11) or npm (0.27.1).
4. **Monaco:** Monarch only, or Monarch + tree-sitter semantic tokens.
5. **Scope:** TPTP + TSTP only, or also SZS output lines.
6. **tree-sitter distribution:** publish from the subdirectory or mirror to a standalone repo.
7. **Licence** of the monorepo, and how the BNF-derived grammars are attributed to TPTP World.
